# Training frameworks + Blackwell (B200/B300) readiness

## RECOMMENDATION
Move to PyTorch and make torchtitan your primary framework, with Megatron-Bridge as the fallback if you hit a wall. The evidence is lopsided: every third-party, at-scale Blackwell pretraining datapoint in 2025-2026 (1,856-GPU Crusoe MXFP8 run, Nebius 256-GPU DeepSeek run, Lambda's 55-60% MFU configs for exactly your 8B class on B200, MLPerf v5.1/v6.0) is PyTorch, while JAX-on-Blackwell evidence funnels solely through MaxText and is mostly NVIDIA-authored. Staying on JAX defensibly would mean abandoning your Keras3 codebase for MaxText anyway — a rewrite either way — and there is zero public precedent for a 7B Keras3 run. torchtitan fits a solo-led project best: small hackable codebase, FSDP2 + async TP/CP/PP, MXFP8 for dense and MoE on Blackwell via TorchAO, DCP async checkpointing with HF interop, and Lambda's whitepaper gives you copyable B200 configs (key trap: Hopper-era defaults cost ~2x — use TP=1 + selective AC on B200 for 7-8B). Megatron-Bridge is the higher-ceiling, higher-complexity option (MLPerf-winning, NVFP4-ready, 30+ model families) — adopt it only if you later need its last 10-15% or NVFP4. Plan to port your Muon hybrid onto FSDP2 yourself (torch.optim.Muon lacks distributed support; torchtitan issue #2494 is open) — a contained 1-2 week task that Kimi K2 and DeepSpeed precedents de-risk.

Precision: run BF16 as the correctness baseline, then switch to MXFP8 (TorchAO/TE 2.16+) after your own 1-2K-step loss-parity A/B — it is the proven Blackwell recipe (BF16-matching convergence per arXiv:2506.08027, 1.22-1.28x demonstrated at 2K-GPU scale), expect a more modest ~1.15-1.25x at 7-8B where quantization overhead bites. Keep embeddings, norms, and lm_head in BF16, and ensure all GEMM K dims are divisible by 32. Do NOT use NVFP4 for this run — real (12B/10T tokens validated) but NVIDIA-internal-only evidence, mandatory exotic techniques, and a one-shot solo run has no budget for divergence forensics. Use FlashAttention-4 (SM100/SM103, PyPI since 2026-07-15) or cuDNN attention via TE. Budget with ~55% MFU BF16 / ~15-20K tok/s/GPU MXFP8 on B200 for a 7B; prefer B300 nodes when available (~12.6% faster, 270GB HBM buys you longer-context batches). Architecture and data should copy the OLMo 3 7B playbook (the only fully-open 7B run) with Qwen3-style staged curriculum for the agentic/long-context phases.

## FULL REPORT
# Training Frameworks + Blackwell (B200/B300) Readiness for a 7B From-Scratch Pretrain — as of 2026-07-23

## 1. Framework landscape (2025–2026 evidence of real >=7B pretraining)

### torchtitan (PyTorch-native, Meta)
- Feature set as of mid-2026: FSDP2 with per-parameter sharding, tensor parallel (incl. async TP), pipeline parallel, context parallel, expert parallel, torch.compile, Float8 **and "MXFP8 training for dense and MoE models on Blackwell GPUs"** stated directly in the README ([github.com/pytorch/torchtitan](https://github.com/pytorch/torchtitan), fetched 2026-07-23). ~5.6k stars, 908 forks; ICLR 2025 paper ([arXiv:2410.06511](https://arxiv.org/html/2410.06511)).
- Release cadence is healthy: v0.2.0 (Oct 2025), v0.2.1 (Dec 2025, DeepEP integration, GPT-OSS model, variable-length attention), v0.2.2 (Feb 2026, FlexCP, DeepEP expert overlap, Context Parallel API updates) ([releases page](https://github.com/pytorch/torchtitan/releases), fetched 2026-07-23; dates inferred from bundled nightly wheel tags, e.g. torch-2.12.0.dev20260220).
- **Largest public Blackwell run of any open framework**: PyTorch team + Crusoe trained Llama3-70B on **1,856 B200 GPUs** with TorchAO MXFP8, 1.22–1.28x speedup over BF16, loss curves "nearly indistinguishable" (MXFP8 slightly ahead), ~5% perf loss scaling 4→188 nodes ([PyTorch blog, 2025-09-03](https://pytorch.org/blog/accelerating-2k-scale-pre-training-up-to-1-28x-with-torchao-mxfp8-and-torchtitan-on-crusoe-b200-cluster/)).
- Second large Blackwell datapoint: DeepSeek-V3 671B on **256 B200** (32 nodes, Nebius), BF16 651 tok/s → +32% with DeepEP → **+41% with MXFP8 grouped-GEMM + DeepEP (918 tok/s)**; 1,500-step loss parity on a 16B MoE; known limitation: torch.compile + TP + MXFP8 linear layers not yet compatible ([PyTorch blog, 2026-03-25](https://pytorch.org/blog/enabling-up-to-41-faster-pre-training-mxfp8-and-deepep-for-deepseek-v3-on-b200-with-torchtitan/)).
- Checkpointing: PyTorch DCP with async checkpointing; checkpoints interoperable with torchtune/HF ([README](https://github.com/pytorch/torchtitan)). Scaling efficiency up to 97% at 1,024 GPUs reported in the B200 benchmark literature ([Lambda MFU whitepaper](https://lambda.ai/hubfs/4.%20Resources/White%20Papers/Lambda%20MFU.pdf)).
- Caveat: still versioned 0.x/"pre-release"; production adopters are not formally listed (Meta-authored; AMD ships an optimized fork since Nov 2025) — treat "who uses it in production" as partially UNVERIFIED beyond Meta/Crusoe/Nebius/Lambda engagements.

### Megatron-LM / Megatron-Core / Megatron-Bridge (NVIDIA)
- NVIDIA restructured NeMo in 2025–2026 into composable libraries: **Megatron-Bridge** (pretraining/SFT/LoRA, PyTorch-native loop, bidirectional HF<->Megatron checkpoint conversion), **NeMo-RL** (post-training), **Automodel** (DTensor alternative). Megatron-Bridge v0.5.1 shipped **2026-07-21**; supports 30+ model families incl. Qwen 3.5 MoE, Gemma 4 MoE, DeepSeek V2–V4, Nemotron-3 ([github.com/NVIDIA-NeMo/Megatron-Bridge](https://github.com/NVIDIA-NeMo/Megatron-Bridge), fetched 2026-07-23).
- Megatron-Core development moved fully into the open on GitHub in Dec 2025; Jan 2026 added Dynamic Context Parallelism (up to 1.48x for variable-length sequences); 2026 Q2 MoE roadmap targets full FP8 + Blackwell optimization ([Megatron-LM issue #4815](https://github.com/NVIDIA/Megatron-LM/issues/4815)).
- Performance ceiling of the ecosystem: NVIDIA's MLPerf Training v6.0 submissions used Megatron-Bridge; DeepSeek-V3 pretraining on GB300 at **1,648 TFLOPS/GPU (6,338 tok/s/GPU)**, up 1.3x from ~1,088 TFLOPS/GPU in Nov 2025 ([Megatron-Bridge README](https://github.com/NVIDIA-NeMo/Megatron-Bridge); [NVIDIA blog](https://developer.nvidia.com/blog/nvidia-blackwell-tops-mlperf-training-6-0-with-industry-leading-scale-and-performance/)).
- NVIDIA's official DGXC benchmarking recipes for Llama 3.1 8B/70B now reference **Megatron-Bridge configs across H100/B200/B300/GB200/GB300 with BF16/FP8/NVFP4** ([dgxc-benchmarking llama3.1 README](https://github.com/NVIDIA/dgxc-benchmarking/blob/main/llama3.1/README.md), fetched 2026-07-23). H100 reference for Llama-3.1-8B FP8: 111,054 tok/s on 8x H100 (~13.9K tok/s/GPU) at 40.6% MFU ([NGC DGXC catalog](https://catalog.ngc.nvidia.com/orgs/nvidia/teams/dgxc-benchmarking/resources/llama31-8b-dgxc-benchmarking-b)).

### MaxText (JAX, Google/AI-Hypercomputer)
- Actively developed; Qwen3.5 35B & 397B support added 2026-06-09 ([github.com/AI-Hypercomputer/maxtext](https://github.com/AI-Hypercomputer/maxtext)). NVIDIA ships monthly JAX containers: 26.06 (July 2026) = JAX 0.10.1, Transformer Engine 2.16, CUDA 13.3, pinned MaxText commit ([NVIDIA JAX 26.06 release notes](https://docs.nvidia.com/deeplearning/frameworks/pdf/JAX-Release-Notes.pdf)); a ~10% MaxText perf gain on B200 and a fixed inter-node FSDP+DDP crash on Blackwell appear in 2026 release notes ([rel-25-04 onward](https://docs.nvidia.com/deeplearning/frameworks/jax-release-notes/rel-25-04.html)).
- **NVFP4 4-bit pretraining recipe on Blackwell is implemented in MaxText**: 1.31–1.73x speedup **over FP8** (Llama-3 8B: 1.35x on GB200, 1.31x on GB300; 405B: up to 1.73x on GB300), attention kept in higher precision, quantization only on MLP GEMMs, +0.026 nats converged-regime gap over 10K steps ([NVIDIA blog, 2026-06-08](https://developer.nvidia.com/blog/train-models-faster-with-jax-and-maxtext-using-nvfp4-on-nvidia-blackwell/)).
- This makes MaxText the **only JAX path with credible public Blackwell pretraining evidence**. Note all NVFP4 numbers are NVIDIA-generated (GB200/GB300), not third-party.

### OLMo-core (Ai2) — the closest "reference 7B" precedent
- OLMo 3 (released Nov 2025): 7B base pretrained on up to **1,024 H100s at ~7.7K tokens/sec/GPU**; 32B at ~1,900 tok/s/GPU; OLMo-core is PyTorch + FSDP; moving SFT into OLMo-core gave 8x throughput ([Ai2 blog](https://allenai.org/blog/olmo3); [muxup cost analysis](https://muxup.com/2025q4/minipost-olmo3-training-cost)). Fully open: data (Dolma 3), code, checkpoints — the best "copy an actual 7B run" artifact in existence. No public Blackwell runs from Ai2 found (UNVERIFIED for B200).

### nanotron (Hugging Face)
- SmolLM3 3B: 11T tokens on **384 H100, 24 days, BF16**, GBS 2.36M tokens, AdamW ([HF SmolLM3 blog](https://huggingface.co/blog/smollm3); [model card](https://huggingface.co/HuggingFaceTB/SmolLM3-3B-Base)). Proven at 3B/384-GPU scale, full configs public; but smaller community than torchtitan/Megatron and no public Blackwell evidence.

### Levanter (JAX, Stanford CRFM / Marin)
- Marin 8B (May 2025) beat Llama-3.1-8B-Base on 14/19 benchmarks; Marin 32B trained openly in late 2025 — but **on TPUs** ([Google Open Source blog, Dec 2025](https://opensource.googleblog.com/2025/12/training-marin-32b-what-an-open-lab-can-build-with-tpus-jax-and-a-little-persistence.html)). Levanter's own docs state GPU support "only tested on Ampere" ([Levanter GPU docs](https://levanter.readthedocs.io/en/latest/Getting-Started-GPU/)). Not a Blackwell-proven path.

### GPT-NeoX, LitGPT, LLMFoundry/Composer
- GPT-NeoX remains Megatron/DeepSpeed-era architecture; last notable initiative found was 2024 post-training work ([EleutherAI blog](https://blog.eleuther.ai/rlhf-and-rlaif-in-gpt-neox/)); no 2025–2026 Blackwell pretraining evidence found (UNVERIFIED staleness, but no positive signal). LitGPT is finetuning-oriented. LLMFoundry: no 2026 activity surfaced in searches — treat as not competitive for this run.

## 2. JAX-on-Blackwell vs PyTorch — is staying on JAX defensible?

- JAX **works** on B200/B300: NVIDIA maintains monthly JAX containers (26.06: CUDA 13.3, TE 2.16), MaxText gets Blackwell optimizations, and NVIDIA/Google jointly promote it ([NVIDIA-Google partnership blog](https://blogs.nvidia.com/blog/nvidia-google-blackwell-gemini/)).
- But the **evidence mass is asymmetric**. Everything with third-party, at-scale Blackwell pretraining numbers — MLPerf v5.1/v6.0 submissions, Lambda's MFU whitepaper, the 1,856-GPU Crusoe run, Nebius' 256-GPU DeepSeek run — is PyTorch (torchtitan or Megatron). JAX Blackwell evidence funnels exclusively through MaxText and is mostly NVIDIA-authored. FP8 scaling-recipe support in JAX is noted as more limited than PyTorch's ([Introl FP8 infrastructure guide](https://introl.com/blog/fp8-training-infrastructure-next-generation-precision-guide)).
- Critically for this project: the old stack is **JAX/Keras3 custom code, not MaxText**. I found **zero public evidence of any >=7B distributed pretraining run using Keras 3** in 2025–2026. Staying "on JAX" defensibly means migrating to MaxText — which is a rewrite anyway, erasing most of the code-reuse argument. muP and Muon learnings transfer conceptually, not as code.
- FlashAttention-4 landed for Blackwell: CuTeDSL implementation for SM100 (B200) and SM103 (B300), paper 2026-03-05, PyPI release 2026-07-15 ([arXiv:2603.05451](https://arxiv.org/html/2603.05451v1); [flash-attn-4 PyPI](https://pypi.org/project/flash-attn-4/); [Together blog](https://www.together.ai/blog/flashattention-4)) — this is a PyTorch-ecosystem asset; JAX gets attention via cuDNN/TE instead.

## 3. Precision on Blackwell: what is proven for a 7B from-scratch run

- **BF16**: always-safe baseline; Together AI reports 90% faster BF16 training on B200 vs H100 with tuned kernels ([Together blog](https://www.together.ai/blog/nvidia-hgx-b200-with-together-kernel-collection)).
- **MXFP8 (block-scaled, 1x32, E8M0 scales) — the proven Blackwell FP8 path.** NVIDIA's recipe paper shows MXFP8-E4M3 on *all* tensors (incl. activation gradients) plus a specific (non-OCP-v1.0) rounding algorithm matches BF16 convergence ([arXiv:2506.08027](https://arxiv.org/abs/2506.08027)). Demonstrated at 1,856-B200 scale with 1.22–1.28x over BF16 and loss parity ([PyTorch/Crusoe blog, 2025-09-03](https://pytorch.org/blog/accelerating-2k-scale-pre-training-up-to-1-28x-with-torchao-mxfp8-and-torchtitan-on-crusoe-b200-cluster/)). Constraint: GEMM K dim % 32 == 0. Per-tensor delayed scaling is the legacy Hopper recipe; on Blackwell the fine-grained block-scaling approach is the recommended direction ([TE docs](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/examples/fp8_primer.html); [Megatron MoE docs report MXFP8 with "minimal loss-curve differences vs BF16"](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/moe.html)). Caveat for 7B: the headline MXFP8 wins are on 70B/MoE; at 8B-class the quantization overhead eats more of the gain (the DeepSeek blog explicitly warns quantization overhead can exceed speedup for small GEMMs) — expect ~1.15–1.25x, benchmark yourself.
- **NVFP4 — real but bleeding-edge.** NVIDIA pretrained a 12B hybrid Mamba-Transformer for **10T tokens in NVFP4**, matching FP8 (MMLU-Pro 62.58 vs 62.62), but only with four mandatory techniques: ~16% of linear layers kept in BF16, 16x16 Random Hadamard Transforms on Wgrad inputs, 2D 16x16 weight scaling, stochastic rounding on gradients ([arXiv:2509.25149](https://arxiv.org/html/2509.25149v1), Sept 2025; follow-up outlier-dynamics paper [arXiv:2602.02047](https://arxiv.org/html/2602.02047v1), Feb 2026). MaxText NVFP4 gives 1.31–1.35x over FP8 for 8B on GB200/GB300 ([NVIDIA blog, 2026-06-08](https://developer.nvidia.com/blog/train-models-faster-with-jax-and-maxtext-using-nvfp4-on-nvidia-blackwell/)). All evidence is NVIDIA-internal; no third-party 7B NVFP4 run found. Not the sensible choice for a solo team's one-shot run.
- **Transformer Engine**: v2.16.1 (2026-06-26) supports FP8 delayed/current scaling, MXFP8, NVFP4 on Blackwell in both PyTorch and JAX/Flax; requires CUDA 12.8+ for Blackwell, cuDNN 9.3+ ([github.com/NVIDIA/TransformerEngine](https://github.com/NVIDIA/TransformerEngine)).

## 5. Muon note (project-specific)

The project's validated Muon hybrid is a differentiator, but framework support is uneven: torch.optim.Muon exists in PyTorch 2.9+ **without distributed support**, and torchtitan has an open feature request (2026-03-05) to enable Muon for large-scale pretraining ([torchtitan issue #2494](https://github.com/pytorch/torchtitan/issues/2494); [pytorch issue #148819](https://github.com/pytorch/pytorch/issues/148819)). Moonshot's Kimi K2 (1T MoE, 15.5T tokens) proves distributed Muon at scale, and DeepSpeed published a Muon integration ([PyTorch blog](https://pytorch.org/blog/using-muon-optimizer-with-deepspeed/)). Porting your JAX Muon-hybrid semantics onto FSDP2 (gather -> Newton-Schulz -> shard) is a contained, well-trodden ~1–2 week task, not a research risk.

## 6. Reference-model context

- Qwen3: 36T tokens, three-stage curriculum (30T at 4K seq, ~5T reasoning-heavy, then 32K long-context), qk-layernorm, internal (non-public) training stack ([arXiv:2505.09388](https://arxiv.org/pdf/2505.09388), May 2025).
- Gemma 4: released 2026-04-02 (E2B/E4B/12B/26B-MoE/31B-dense, 256K context, Apache 2.0) — trained on Google's internal JAX/TPU stack, not reproducible externally ([Google blog](https://blog.google/innovation-and-ai/technology/developers-tools/gemma-4/)).
- OLMo 3 is the only reference model whose *entire* 7B training config is runnable by you ([Ai2](https://allenai.org/blog/olmo3)).
