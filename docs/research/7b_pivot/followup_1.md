# FOLLOWUP: Engineering scope, tooling, and cost of the agentic RL environment / verifiable-reward fleet

The agentic post-training plan specifies the RL algorithm (GRPO/RLVR via verl or SkyRL) and correctly notes rollout throughput (vLLM/SGLang) will bottleneck, but NO dimension scoped the environment infrastructure — the sandboxed code/terminal execution, SWE-repo Docker harnesses, tool-execution services, verifiable reward computation, and the orchestration to run hundreds of thousands of concurrent multi-turn rollouts with flaky-environment and reward-hacking handling. For an agentic model this environment fleet IS the substance of the RL stage, not a detail, and it is the usual place small/solo teams stall for months. The current plan budgets agentic RL at 5-15% of pretraining FLOPs and 'weeks not months,' which almost certainly ignores the environment-building and operations effort. Getting this wrong changes the timeline, the cost, and whether the headline agentic targets (SWE-bench Verified 15-25%, Terminal-Bench 2.0, tau2-bench) are reachable at all.

## RECOMMENDATION
Do not build environments; assemble them. Adopt SkyRL (skyrl-train + skyrl-agent) or verl as the trainer and standardize every custom environment on verifiers/OpenEnv APIs; source SWE tasks from SWE-rebench's 7,500 pre-built images plus R2E-Gym's 8.1K tasks (decontaminated against SWE-bench Verified repos), train inside the OpenHands scaffold you will be scored on, use Harbor for Terminal-Bench-style rollouts, and tau2's Gymnasium environment plus a handful of verifiers-built tool domains for function-calling RL. Run the environment fleet on Kubernetes from day one (DeepSWE's plain-Docker attempt crashed) sized at roughly 16-32 CPU cores per training GPU (~1,000-2,000 cores for a DeepSWE-geometry run), or skip the K8s build entirely by renting Prime Intellect/E2B/Modal sandboxes for $2k-8k per campaign — the dollars are negligible next to the engineering time. Critically, sequence the capability plan the way the evidence points: SWE-smith showed 40.2% SWE-bench Verified is reachable at 32B with SFT on 5k trajectories and *no RL*, and Qwen3-8B itself was distilled rather than RL-trained — so drive most of the agentic capability through large-scale trajectory SFT/rejection sampling first, and treat GRPO/RLVR as a final 4-8 week polish stage on top.

Re-budget honestly: the "5-15% of pretraining FLOPs, weeks not months" line should be revised to ~3-5 months of solo-lead calendar time for the full agentic post-training stage (environment integration 2-4 weeks, reward hardening and anti-hacking gates 2-4 weeks, RL campaigns and evals 4-8 weeks, tool/terminal domains 3-6 weeks), with GPU cost for the 7B RL stage itself modest (order 1,000-2,500 B200-hours, UNVERIFIED estimate). Also reset the headline target: no verified open 7-8B model currently documents 15-25% on SWE-bench Verified — treat 15% (OpenHands scaffold) as the success line and 20%+ as stretch, or be prepared to accept that the published wins at those scores all happened at 32B.

## FULL REPORT
# The Agentic RL Environment Fleet: Scope, Tooling, and Cost for a Solo-Led 7B Post-Training Effort

**Method note:** this session's WebSearch budget was exhausted by sibling agents, so all grounding below comes from direct WebFetch of primary sources (GitHub repos, arXiv papers, vendor pricing pages), all fetched 2026-07-23. Anything I could not confirm live is marked UNVERIFIED.

## 1. Bottom line

The good news: in 2025-2026 the environment layer stopped being a build-from-scratch problem. There are now (a) executable SWE-task hubs with tens of thousands of pre-built Docker task instances (SWE-rebench, R2E-Gym, SWE-smith, SWE-Gym), (b) environment-abstraction frameworks with trainer integrations (SkyRL-Gym/skyrl-agent, verifiers + Environments Hub, OpenEnv, Harbor, tau2's Gymnasium env), and (c) rentable sandbox fleets (E2B, Modal, Daytona, Prime Intellect) with published per-second pricing. The bad news: every documented end-to-end agentic-RL run that actually moved SWE-bench numbers was a multi-person, multi-week infrastructure effort even *with* these components, and no 7-9B open model has published a full executable-environment agentic RL recipe you can copy. "Weeks not months" for the whole RL stage is not supported by the evidence; 3-5 months of the solo lead's calendar time is the realistic envelope, with GPU FLOPs being the *cheapest* part of it.

## 2. What exists to reuse (Q1)

### Executable SWE-task hubs (the core asset class)

- **SWE-Gym** ([github.com/SWE-Gym/SWE-Gym](https://github.com/SWE-Gym/SWE-Gym), ICML 2025, [arXiv:2412.21139](https://arxiv.org/abs/2412.21139)): 2,438 real tasks from 11 Python repos plus a 234-instance Lite split, with pre-built Docker images (avg 2.6 GB, **6 TB total**). Integrates with OpenHands and Moatless scaffolds; their fine-tuned 32B OpenHands agent reached 32% SWE-bench Verified with a trained verifier. Critical data point: building it took "**around 200 human annotation hours and 10k CPU core hours**" for manual dependency setup and validation ([arXiv HTML](https://arxiv.org/html/2412.21139v1), fetched 2026-07-23).
- **R2E-Gym** ([github.com/R2E-Gym/R2E-Gym](https://github.com/R2E-Gym/R2E-Gym), COLM 2025, [arXiv:2504.07164](https://arxiv.org/abs/2504.07164)): **8.1K tasks across 13 repos**, generated from *commits* (SWE-Gen procedure) rather than human PRs — much cheaper curation. Ships Docker images (~300-500 MB each per the project site), a Python gym API, and parallel-worker support ([r2e-gym.github.io](https://r2e-gym.github.io/)). This is the dataset both DeepSWE and SkyRL-Agent trained on.
- **SWE-smith** ([github.com/SWE-bench/SWE-smith](https://github.com/SWE-bench/SWE-smith), NeurIPS 2025 Spotlight, [arXiv:2504.21798](https://arxiv.org/abs/2504.21798)): a task-*generation toolkit* — **52,000 task instances**, **250+ Docker environments (one image per repo)**, 26k agent trajectories. Their SWE-agent-LM-32B hit **40.2% pass@1 on SWE-bench Verified via SFT on 5k trajectories alone** — no RL — which is strategically important (see §6).
- **SWE-rebench** ([huggingface.co/datasets/nebius/SWE-rebench](https://huggingface.co/datasets/nebius/SWE-rebench)): **21,000+ issue-PR pairs from 3,400+ Python repos**, fully automated pipeline (LLM-driven environment-setup extraction and quality labeling), **7,500 pre-built Docker images on Docker Hub**, CC-BY-4.0, continuously updated. Largest ready-made pool; you inherit their images rather than building your own.

### Environment frameworks / abstraction layers

- **SkyRL** ([github.com/NovaSky-AI/SkyRL](https://github.com/NovaSky-AI/SkyRL), v0.3.0, 2026-07-17): skyrl-train (trainer), **skyrl-gym** ("gymnasium of tool-use tasks, including a library of math, coding, search and SQL environments"), and **skyrl-agent** for long-horizon agents (SWE, web research, MemAgent tasks; backends: vLLM/OpenAI-compatible serving, verl, SkyRL-train, Tinker) ([skyrl-agent README](https://raw.githubusercontent.com/NovaSky-AI/SkyRL/main/skyrl-agent/README.md)). Harbor integration for terminal agents landed 2026-02-17. This is currently the closest thing to a turnkey "agentic RL environment + trainer" stack.
- **verl** ([github.com/volcengine/verl](https://github.com/volcengine/verl), v0.8.0, 2026-06-01): multi-turn tool-calling agent loop, **SandboxFusion integration** for code rewards, vLLM/SGLang backends, server-based RL and partial rollout. **SandboxFusion** itself ([github.com/bytedance/SandboxFusion](https://github.com/bytedance/SandboxFusion)) is ByteDance's self-hostable code-judging sandbox: 24 languages, 12 built-in benchmark judges, Docker deployment — good for single-shot code-RL rewards, not for full repo environments.
- **verifiers + Environments Hub** ([github.com/PrimeIntellect-ai/verifiers](https://github.com/PrimeIntellect-ai/verifiers), v0.2.1, 2026-07-20; [Hub announcement 2025-08-27](https://www.primeintellect.ai/blog/environments)): a library for building multi-turn/tool environments with rubric rewards, a community hub ("over 30 researchers and companies contributed environments" at launch), hosted sandboxes, and direct integration with prime-rl. Prime's stated thesis matches your gap analysis: "if high-quality environments remain expensive and closed, open-source models will fall further behind."
- **OpenEnv** ([github.com/meta-pytorch/OpenEnv](https://github.com/meta-pytorch/OpenEnv), v0.4.1, July 2026, BSD-3): the emerging *standard* — Gymnasium-style `step()/reset()/state()` over FastAPI/WebSocket servers in Docker, governed by Meta-PyTorch, Hugging Face, NVIDIA, Microsoft, Prime Intellect, Modal, Fleet AI, Mercor et al.; integrations with torchforge, TRL, **SkyRL**, Unsloth, ART. Writing your custom environments against OpenEnv (or verifiers) future-proofs them across trainers.
- **Harbor / Terminal-Bench 2.0** ([github.com/laude-institute/harbor](https://github.com/laude-institute/harbor), v0.20.0, 2026-07-18; [github.com/laude-institute/terminal-bench](https://github.com/laude-institute/terminal-bench)): the official TB-2.0 harness; runs containerized agent rollouts "across thousands of environments in parallel," can "generate rollouts for RL optimization," and natively drives cloud sandbox providers "Daytona, Modal, LangSmith, Blaxel, and Novita Sandbox" (example: 4 concurrent locally → 100 concurrent on Daytona).
- **tau2-bench** ([github.com/sierra-research/tau2-bench](https://github.com/sierra-research/tau2-bench), v1.0.1, July 2026; [arXiv:2506.07982](https://arxiv.org/pdf/2506.07982)): **200 tasks** (airline 50, retail 100, telecom 50) built from policy documents + tool APIs + database state + an LLM user simulator; the repo now ships **a Gymnasium-compatible environment for RL**, not just eval. Note the scale: a funded research lab produced only ~200 tasks across 3 domains — hand-built tau-style domains are expensive per task.
- **OpenHands runtime** ([docs.openhands.dev/usage/architecture/runtime](https://docs.openhands.dev/usage/architecture/runtime)): client-server Docker action-execution server (bash + browser + plugins over REST), with Docker/Local/Remote runtime options; SWE-Gym explicitly used "OpenHands's remote runtime feature to parallelize evaluation." Since your SWE-bench target is scored on the OpenHands scaffold, training *in* this scaffold (as SWE-Gym did) is the aligned choice.

## 3. Sandboxed execution at rollout scale + CPU footprint (Q2)

Published anchors for what sits beside the GPU cluster:

- **DeepSWE (Agentica/Together, 2025-07)** ([together.ai/blog/deepswe](https://www.together.ai/blog/deepswe)): Qwen3-32B trained on **64 H100s for 6 days** over ~4.5K R2E-Gym tasks. Each RL iteration spawned "**512 (BS=64, 8 passes) Docker containers in parallel**"; plain Docker **crashed the daemon at scale**, so they "integrated Kubernetes support into R2E-Gym," scaling to "**beyond 1000 CPU cores**." Rule of thumb this implies: **~16+ CPU cores per training GPU** of side-fleet for SWE-style RL at 32B; a 7B run with the same batch geometry needs the same *environment* fleet even though the GPU count drops.
- **Kimi K2** ([arXiv:2507.20534](https://arxiv.org/html/2507.20534v1)): RLVR gym backed by "robust sandbox infrastructure, powered by Kubernetes… supports **over 10,000 concurrent sandbox instances**"; heavy environments are "deployed as dedicated services that can scale up more easily," with "a large number of concurrent rollouts to amortize latency." Their agentic data pipeline used "3000+ real MCP tools" plus "over 20,000 synthetic tools" with a tool *simulator* plus "real execution sandboxes… particularly in coding."
- **Qwen3-Coder** ([qwenlm.github.io/blog/qwen3-coder](https://qwenlm.github.io/blog/qwen3-coder/)): "a scalable system capable of running **20,000 independent environments in parallel**" on Alibaba Cloud for long-horizon SWE RL. That is the frontier-lab end of the spectrum — not your target, but it shows where the headroom goes.
- **Isolation tech:** E2B's open-source backend runs sandboxes on **Firecracker microVMs** (Apache-2.0, self-hostable via Terraform on GCP, AWS beta) ([github.com/e2b-dev/infra](https://github.com/e2b-dev/infra)). For SWE-repo tasks, everyone documented above (SWE-Gym, R2E-Gym, SWE-rebench, DeepSWE) used **plain Docker containers orchestrated by Kubernetes**, not microVMs — trusted-ish workloads (your own model's code against known repos) make containers acceptable; microVMs matter more for hostile/multi-tenant code.
- **Storage is non-trivial:** SWE-Gym's images total **6 TB**; SWE-rebench ships 7,500 images; plan a local registry/cache and image-GC on every node.

**Rentable sandbox fleets (verified pricing, fetched 2026-07-23):**

- **E2B** ([e2b.dev/pricing](https://e2b.dev/pricing)): 2 vCPU $0.000028/s + RAM $0.0000045/GiB/s (≈$0.17/h for 2 vCPU+4 GiB); Pro $150/mo, 24-h sessions, 100 concurrent (extendable to 1,100).
- **Modal** ([modal.com/pricing](https://modal.com/pricing)): sandboxes $0.00003942/core/s + $0.00000667/GiB/s (≈$0.19/h for 1 core+2 GiB); also H100s at $0.001097/s.
- **Prime Intellect sandboxes** ([docs.primeintellect.ai](https://docs.primeintellect.ai/sandboxes/overview)): $0.05/core/h + $0.01/GB/h (≈**$0.08/h** for 1 CPU/2 GB/10 GB); account cap **512 active sandboxes / 512 cores** — right-sized for a DeepSWE-scale run.
- **Daytona** ([daytona.io/pricing](https://www.daytona.io/pricing)): usage-based, $200 free credits; page showed $0.0858/vCPU/h for Windows runtimes; Linux rate not captured (UNVERIFIED detail).

## 4. What published runs say about effort, flakiness, and reward hacking (Q3)

- **Environment construction effort:** SWE-Gym: 200 human hours + 10k CPU-core-hours for 2.4k instances across just 11 repos, chosen from 358 candidates because manual setup was the bottleneck ([arXiv:2412.21139](https://arxiv.org/html/2412.21139v1)). R2E-Gym and SWE-rebench exist precisely to automate this away — reuse them.
- **Flakiness/scale failures:** DeepSWE's Docker-daemon crashes → Kubernetes rewrite is the canonical story; their reward is a sparse 0/1 on "a selected sample of tests" with a **5-minute timeout**, i.e., they deliberately subsampled tests to bound env latency ([Together blog](https://www.together.ai/blog/deepswe)). tau2-bench formalizes environment/user-simulator nondeterminism with pass^k, showing success degrades as k grows ([arXiv:2506.07982](https://arxiv.org/pdf/2506.07982)) — budget for per-task repeat sampling in your eval gates.
- **Reward hacking:** DeepSWE used "compact filtering" — masking trajectories that hit context/step/time limits so the policy can't harvest reward from accidental terminal states. Kimi K2 added "prescriptive rubrics that aim to eliminate reward hacking" and a self-critic continuously re-grounded on verifiable-reward rollouts ([arXiv:2507.20534](https://arxiv.org/html/2507.20534v1)). Standard SWE-env hygiene (hold out and hide evaluation tests, block test-file edits, decontaminate against SWE-bench-Verified repos — DeepSWE filtered same-repo tasks) is visible across these reports.
- **Throughput engineering:** SkyRL-Agent ([arXiv:2511.16108](https://arxiv.org/html/2511.16108v1), 2025-11) trained SA-SWE-32B to **39.4% SWE-bench Verified in 4,601 H100-hours** (vs DeepSWE's 9,180 H100-hours for 42.2%) on the same 4.5K R2E-Gym tasks, crediting an async pipeline dispatcher (1.55× over naive async batching, ~90% GPU util). The GPU-side lesson: naive synchronous rollouts waste roughly half your compute; use a framework that already solved this.

## 5. Did any 7-9B open model document its agentic-RL environment fleet? (Q4)

**Effectively no — this is the key sobering finding.**

- **OLMo 3 (7B/32B)** ([allenai.org/blog/olmo3](https://allenai.org/blog/olmo3), 2025-11-20): the most transparent recipe available, but its RLVR stage uses the Dolci "hard, diverse prompts across math, coding, instruction following, and general chat" — **prompt-level verifiable rewards, not interactive executable environments**; function calling comes from SFT/DPO data. Post-training ran on 256 H100s with Open Instruct.
- **Nemotron Nano 2 (9B/12B)** ([arXiv:2508.14444](https://arxiv.org/html/2508.14444v2)): tool calling trained with SFT + **DPO against "WorkBench,"** a mock-API environment where "correctness [is] verified through database state comparisons" (BFCL v3 66.98 vs Qwen3-8B 66.34). A lightweight simulated-tool environment, not a sandbox fleet.
- **Qwen3-8B** ([arXiv:2505.09388](https://arxiv.org/html/2505.09388v1)): lightweight Qwen3 models were built by **strong-to-weak distillation** from the flagship, "requiring only 1/10 of the GPU hours compared to the four-stage training method" — i.e., your reference target model itself likely did *not* go through the full agentic RL pipeline (the paper doesn't enumerate which sizes; the 8B-specifically claim is high-confidence but UNVERIFIED at the sentence level).
- **gpt-oss-20b** ([huggingface.co/openai/gpt-oss-20b](https://huggingface.co/openai/gpt-oss-20b)): model card documents harmony format and agentic capabilities but **no RL environment infrastructure, task counts, or sandbox details**. **SmolLM3**: UNVERIFIED (not fetched), but no known executable-env RL claim.

The documented executable-environment RL successes (DeepSWE 42.2%, SA-SWE-32B 39.4%, R2E-Gym-32B 34.4%, SWE-agent-LM-32B 40.2%) are all **32B models**. At 7B scale, the only published anchors I could verify are weak: SWE-Gym's 7B Moatless result was ~10% on SWE-bench *Lite*. Your 15-25% SWE-bench Verified target for a 7B under OpenHands is **beyond any published open 7B result I could verify** (UNVERIFIED that any open 7-8B exceeds ~15% SBV as of today) — treat 15% as the stretch success line, not the floor.

## 6. Build-vs-reuse map, effort, and cost (Q5)

**Reuse (do not build):** SWE task instances + Docker images (SWE-rebench 21k/7.5k images → R2E-Gym 8.1k → SWE-smith toolkit for infinite synthesis); agent harness (OpenHands runtime — also your eval scaffold); trainer + env API (SkyRL or verl; both integrate the above ecosystems, SkyRL-agent has SWE + Harbor paths already wired); terminal tasks (Terminal-Bench 2.0 via Harbor, which already does parallel cloud sandboxes and RL rollout generation); tau2's Gymnasium env for tool-use RL and eval; SandboxFusion or verifiers sandboxes for single-shot code rewards; OpenEnv/verifiers as the spec for anything custom.

**Build (small, unavoidable):** (a) your function-calling/tau-style domain environments beyond tau2's 200 tasks — via verifiers/OpenEnv, expect days per domain but weeks to make rewards non-hackable; (b) reward services + trajectory filtering (compact filtering, test-hiding, decontamination); (c) the K8s glue: a container pool with image pre-pull, per-rollout timeouts, retry/quarantine for flaky tasks, and metrics.

**Compute/cost envelope for one serious SWE-RL campaign (7B, DeepSWE-like geometry, 512 concurrent envs, ~200 steps):** sandbox side ≈ 25k-50k sandbox-hours ≈ **$2k-8k** on managed fleets (Prime/E2B/Modal rates above) or ~1,000-2,000 CPU cores self-hosted on K8s for ~a week; GPU side for a 7B should land **well under** SA-SWE-32B's 4,601 H100-hours — call it 1,000-2,500 B200-hours including restarts (my estimate, UNVERIFIED). Storage: 1-6 TB of images + registry. The dollars are small; **the person-time is the cost**: DeepSWE (a multi-person team, standing on R2E-Gym) still needed a Kubernetes rewrite mid-project, and SWE-Gym burned 200 hours on environments alone. Realistic solo-lead calendar: **2-4 weeks** to first stable end-to-end SWE rollout loop on a reused stack, **4-8 weeks** of RL runs/reward-debugging/eval gating, **plus 3-6 weeks** for tool-use/terminal domains — **~3-5 months for the RL stage overall**, versus the plan's "weeks." Buying managed environments (Prime Intellect Hub + hosted sandboxes, Harbor + Daytona/Modal) is a real option that removes the K8s build but not the reward-design or integration work.
